# T1.2 — Per-Position Volatility Parity (design doc)

> 2026-04-29. Pre-implementation design for the Tier-1 vol-targeting item in `RESEARCH_PLAN_2026-04-29.md`. Implementation deferred until the gap-analysis fork lands and refines the integration points below.

## What we're actually building (honest framing)

The synthesis called this "portfolio-level realized-volatility targeting." That's the literature label (Carver, Barroso & Santa-Clara, etc.) — and it assumes a **portfolio constructor** that decides allocations across all symbols simultaneously, then scales the whole book to a target vol.

The bot's architecture is **per-position decisions** (`services/trading-engine/app/live_trading.py:130-150`: each order is sized and submitted independently when an aggregator signal arrives). There is no central place that sees "all symbols' positions at once" and rescales the book.

So what's actually implementable today is **per-position vol parity**:

```
size_i = baseline_size × (target_vol_per_position / realized_vol_i)
```

Each new entry contributes the same expected volatility. This captures most of the documented benefit (mitigates oversize on high-vol regimes, undersize on low-vol) without inventing a portfolio constructor that doesn't exist.

If/when the user wants true portfolio-level vol targeting later, that's a separate, larger build (introduce a portfolio aggregator that batches signals across symbols at the bar boundary, then rescales — substantially bigger lift).

## Sizing wrapper

```python
def vol_parity_size(
    baseline_size: Decimal,
    realized_vol_annualized: float,
    target_vol_annualized: float,
    cap_multiplier: float = 3.0,
) -> Decimal:
    """
    Returns size scaled so the position contributes target_vol of risk.
    Capped at cap_multiplier × baseline_size to avoid blow-up when
    realized_vol is near zero. Falls back to baseline_size when
    realized_vol_annualized is None or <= 0.
    """
```

- Cap at 3× baseline is the same defensive shape as Carver's `vol_target_capped`. Without a cap, low-vol regimes can produce arbitrarily large positions.
- Floor: realized_vol clamped to a minimum (e.g., 5% annualized) before division — mathematical robustness.

## Integration points (need fork output)

Candidate sites where vol-parity sizing should hook in:

1. **`auto_trader.py` position-opening path** — likely the cleanest single point if the bot computes a quantity here and that flows to live_trading.py.
2. **`live_trading.py:130-150`** — already has `order.quantity` set when it arrives. Either rescale here (post-decision) or earlier (pre-decision).
3. **A new `risk/vol_targeting.py` module** that wraps the existing position-sizing logic.

The right answer depends on whether per-trade caps (commit `39352ba`) and the auto-trader risk overlay (commit `bef66cb`) compose linearly with vol parity, or whether they need to interact (e.g., vol parity computes desired size, then per-trade cap clamps it). The fork's risk-module map answers this.

**Architectural rule to encode whatever the answer:** vol parity is an **outer overlay** above per-trade caps. Sequence:

```
desired_size = vol_parity_size(baseline, realized_vol, target_vol)
final_size   = min(desired_size, per_trade_cap_size)
```

Vol parity can shrink positions but never increases them past the per-trade cap. This is strictly tighter than current behavior in worst case.
