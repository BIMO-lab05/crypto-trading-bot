# T0.1 — GRU Rebuild on a Returns Target (design doc)

> 2026-05-01. Pre-implementation design for the Tier-0 GRU rebuild flagged
> in `V0-RESULTS-no-edge.md` and listed as open thread #2 of
> `SESSION-2026-04-30-handoff.md` §8. Implementation deferred until the
> user picks among the open questions in §6.

## 1. What we're actually building (honest framing)

The production GRU's marquee R²=0.99 was autocorrelation noise (V0 finding,
commit `c56765c`). Trained on raw close prices, it learned "price is
nearly persistent" — which any naive baseline gets for free. On the
target that actually matters (log-returns), measured R² is **negative**
on every symbol (SOL −0.45, BNB −5.5, ADA −0.36) and corrected directional
accuracy sits at coin-flip (47.9 – 51.4 %).

This rebuild reframes the model: **target log-returns directly, validate
with CPCV + DSR, deploy only when pre-flight gates clear.** If no
configuration clears the gates, the honest answer is "no measurable edge"
and `ENABLE_ML_PREDICTIONS` stays `false`.

**This is *not* a "tune the existing model" task.** The existing target,
loss, and feature mix are all suspect under the V0 finding. We rebuild
the trainer's target/loss/features, keep the artifact contract
(`scalers.pkl`, `model.h5`, `metadata.json`, now `eval_arrays.npz`)
and the deployment plumbing.

## 2. Target reformulation

Trainer currently sets `target_col='close'` (raw price level). The rebuild
swaps this to log-returns:

```
y_t = log(close_{t+1} / close_t)        # 1-bar log-return
```

Two viable model forms — pick one before implementation (Q1 below):

**Form A — regression on log-return.**
- Output layer: 1 neuron (or `prediction_horizon` neurons for multi-step).
- Loss: Huber (robust to fat tails) over MSE — crypto returns are heavy-
  tailed and a single 6σ bar can dominate MSE training.
- Sharpe-relevant signal: continuous magnitude of expected return.

**Form B — classification on direction.**
- Output layer: 3-class softmax over `{sign(y) ∈ {-1, 0, +1}}` with a
  flat-zone threshold (e.g. `|y| < 0.001` → 0).
- Loss: class-balanced cross-entropy (the long/short classes are roughly
  balanced for crypto; the flat class is rare → upweight it).
- Sharpe-relevant signal: directional vote, used as `+1/0/-1` position.

Form A retains the existing artifact shape (one float per horizon step).
Form B changes the artifact and the inference path in
`ml-prediction-service/app/ml_models/gru_model.py`. Form A is the
smaller blast radius; Form B is the more honest framing for a
directional bet but adds plumbing.

## 3. Feature reformulation

Current feature set (22 indicators in `prepare_features`) mixes
non-stationary (`sma_7`, `sma_14`, `bb_middle`, `volume`) with stationary
(`returns`, `log_returns`, `rsi`, `macd`, `volatility_*`). Non-stationary
inputs alongside MinMax scaling let the model fit drift instead of skill.

Proposed stationary-only feature set (Q2 below):

- Drop: `sma_*`, `ema_*`, `bb_middle`, `bb_upper`, `bb_lower`, `volume_sma`,
  `high_low_ratio` (level-relative — already roughly stationary, but
  redundant with returns).
- Keep: `returns`, `log_returns`, `volatility_7`, `volatility_14`, `rsi`,
  `macd`, `macd_signal`, `macd_hist`, `bb_width` (bands as ratios),
  `volume_ratio`, `momentum_7`, `momentum_14`.
- Add: log-volume change, realized vol of vol (`std(volatility_7, 14)`),
  intraday range / overnight range ratio, time-of-day cyclical encoding
  (sin/cos of UTC hour) — crypto's session structure matters.

The MinMaxScaler step still runs but on stationary inputs the fit-window
drift problem disappears.

## 4. Validation pipeline (uses today's CPCV wiring)

Already in place after commits `29a27fd` / `d49bfa0` / `679e473` / `7c7b7ab`:

- `_calculate_cpcv_metrics` runs evaluation-time CPCV on the test set,
  emits `test_dsr` + per-path Sharpe distribution into the metrics dict.
- `eval_arrays.npz` (actual / pred / last_close) persists alongside the
  model so risk-metrics-service can re-run CPCV with different
  group / horizon / embargo settings later.
- `model_validator._check_dsr_gate` reads `test_dsr` and (when
  `retrain_min_dsr` is set) blocks deployment.

Pre-flight gate composition for the rebuild — **all must clear**:

| Metric | Threshold | Source |
|---|---|---|
| `test_r2_returns` | `> 0.0` | `returns_metrics.py` (already emitted) |
| `test_dir_acc_corrected` | `> 0.55` | `returns_metrics.py` (already emitted) |
| `test_dsr` (CPCV) | `> 0.95` | `cpcv_evaluation.py` (already emitted) |
| Forward-paper Sharpe (≥7 days, fees + slippage) | `> 0.5` | manual, post-train |

The first three gates land via `retrain_min_r2_returns`,
`retrain_min_dir_acc`, and the existing `retrain_min_dsr` settings. The
forward-paper gate is operator-driven (set the flag, watch for ≥7 days,
read `risk-metrics-service`).

## 5. Phased commit plan

Each chunk independently reverts. Default behaviour unchanged until
chunk 5 lands a passing model.

1. `feat(ml-retraining): add target_mode setting (price | log_returns)` —
   new `retrain_target_mode` setting, default `"price"` for backwards-
   compat. Trainer reads it; passes through to `create_sequences`. Tests
   on both modes (synthetic data only).
2. `feat(ml-retraining): stationary-only feature set behind a flag` —
   new `retrain_feature_set` setting (`"legacy"` | `"stationary"`).
   Default `"legacy"`. New helper `prepare_stationary_features`. Tests
   that the columns and stationarity asserts (ADF p-value < 0.05 on
   each kept feature) pass.
3. `feat(ml-retraining): pre-flight gates (R² returns + dir-acc) in validator` —
   new `retrain_min_r2_returns` and `retrain_min_dir_acc` settings,
   defaults `None` (informational). The existing `_check_dsr_gate` is
   shaped DSR-specifically (hard-coded `'dsr'` key, `retrain_min_dsr`
   field name, "DSR" in the reason text). First step of this chunk is
   a refactor: extract `_check_optional_gate(name, value, threshold,
   *, label, missing_note, info_note, ...)` and rewrite
   `_check_dsr_gate` as a one-liner over the new helper. Then the two
   new gates land as one-liners too. Existing 10 DSR tests must keep
   passing untouched.
4. `chore(ml-retraining): rebuild script — train all symbols on
   target_mode=log_returns + stationary features, dump CPCV report` —
   one-shot Python script, no service changes. Reads existing data via
   `data_collector`, trains, prints DSR / R²-returns / dir-acc per
   symbol. Output committed to `docs/strategy/research-2026-04-29/`.
5. **Decision point** (no code yet): if any symbol clears all four
   gates, ship a deploy commit that flips the active model + sets
   `retrain_min_dsr=0.95` / `retrain_min_r2_returns=0.0` /
   `retrain_min_dir_acc=0.55`. If none clear, ship a doc commit
   recording "no edge found at this horizon / feature set" and leave
   `ENABLE_ML_PREDICTIONS=false`.

Chunks 1 – 3 are reversible code that adds optional knobs; existing
production training is unaffected. Chunk 4 is research output. Chunk 5
is the only one that can change live behaviour.

## 6. Open questions for the user

Block on these before chunks 1 – 4 start.

- **Q1: Form A (regression on log-returns) or Form B (3-class direction)?**
  Form A keeps the existing artifact contract; Form B adds plumbing in
  `ml-prediction-service` but is the more honest framing.
- **Q2: Stationary-only feature set as proposed in §3, or hold the line
  on the legacy 22-indicator pile?** Stationary-only is the academically
  defensible choice; the legacy set is what every paper-trade so far has
  used and the 22 indicators do encode some real signal independent of
  the level series.
- **Q3: Architecture — keep the 2-layer GRU (128, 64), shrink to a
  single-layer GRU (32), or run a non-DL control (XGBoost / linear)
  alongside as a baseline?** Big nets overfit on low-SNR returns; small
  nets / linear baselines often equal them. A single non-DL control
  forces honesty about what skill the GRU is contributing.
- **Q4: Training universe — stick with SOL / BNB / ADA, or expand to the
  ETH / BTC / XRP set the validation layer accepts?** SOL / BNB / ADA is
  the documented production allocation; the wider set may have stronger
  microstructure signal but BTC requires a memory bump (CLAUDE.md
  gotcha).
- **Q5: Acceptance gate composition — all four (R²-returns, dir-acc,
  DSR, forward-paper Sharpe) or a subset?** Stricter is safer but may
  rule out every model; weaker risks shipping noise. The four-gate
  proposal in §4 is the conservative default.

## 7. Risks

- **The most likely outcome is "no model clears the gates."** That is
  the V0 finding compounded — current architecture + features + target
  are mismatched, and even after fixing the target the marginal lift
  from a small recurrent net on hourly crypto bars is probably below
  the noise floor. Plan for this: chunk 5's "no edge found" branch is
  not a failure, it's a result. Ship the doc, leave ML disabled.
- **WSL2 3.7 GiB RAM ceiling.** Already a documented gotcha for BTC
  retrains. Single-layer / smaller-feature configs help; the legacy
  2-layer (128, 64) on the wider feature set is borderline.
- **Selection bias on architecture sweeps.** If we try N architectures
  and pick the best by DSR, the DSR's `num_trials` count understates
  the search. Mitigation: log every trial's DSR explicitly, so
  Bailey-López-de-Prado's expected-max correction can use the real
  count rather than `num_trials = n_paths` from a single sweep.
- **Returns autocorrelation violates CPCV's i.i.d. assumption.**
  Already documented at `cpcv_evaluation.py` and `cpcv.py`. Per-path
  Sharpes are mildly anticonservative trials. The four-gate composition
  guards against any single metric being the deciding factor.
- **The "next bar log-return" target may be the wrong horizon.** Crypto
  hourly returns at the 1-bar horizon are extremely noisy; longer
  horizons (4-bar, 24-bar) carry more signal but trade off against
  position turnover. Q3 / Q5 partly address this; a follow-up T0.1.1
  may sweep horizons.

## 8. What this doc is *not*

- Not a green-light to start the rebuild. The questions in §6 must be
  answered first, in part because the answers affect the chunk-1 code.
- Not a commitment that any model will ship. Chunk 5's "no edge found"
  branch is the honest-ships-nothing path.
- Not a replacement for the forward-paper-test gate. Even a passing
  CPCV/DSR result must clear ≥7 days of paper trading at realistic
  fees + slippage before the model influences real-money trading.
