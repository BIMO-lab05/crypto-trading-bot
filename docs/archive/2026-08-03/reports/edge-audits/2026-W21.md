## Red flags

Numbered. Includes W19 carry-overs that have not resolved.

1. **Bot un-paused without fresh walk-forward results.** Today's
   `b03f4d9` + `456ece3` + `aa1db8d` removed `EMERGENCY_STOP` and
   re-armed the kill-switch path. ADR-013 §B explicitly requires
   walk-forward OOS Sharpe > 1.0 + DSR > 0.95 before re-arming.
   The only walk-forward results on disk are 5 months stale and
   show OOS Sharpe -7.5 to -8.5 on every symbol. **The gate was
   not cleared. The un-pause was not justified by the harness.**
   This is the same dishonest-edge loop ADR-013 was filed to break.
   If trades start firing tonight, the audit cannot honestly call
   any P&L "edge" — it is unfalsified noise against a harness that
   says the strategy loses.

2. **5% daily-loss cap drifted to 10%.** W19's runtime-check found
   `MAX_DAILY_LOSS_PCT=10.0` in `services/trading-engine/.env`,
   double the CLAUDE.md project rule ("5% daily-loss
   circuit-breaker (always)"). Still 10.0 today. No ADR explains
   the doubling. Combined with the 10% per-trade paper cap
   (ADR-010), the bot can lose 10% of the account in one trade
   before the daily-loss brake triggers. On a re-armed bot this
   matters today.

3. **Dead env-var landmines.** `.env` at repo root contains
   `MAX_DAILY_LOSS=0.10` and `ENABLE_AUTOMATIC_TRADING=true` —
   W19 flagged both as **ignored by code**. Real flag names are
   `MAX_DAILY_LOSS_PCT` and `AUTO_TRADING_ENABLED`. Operator may
   read repo-root `.env` and assume those values are in effect.
   They are not. No fix since W19.

4. **W20 audit was never filed.** `reports/edge-audits/` contains
   only W19. The scheduled task either did not run last week or
   produced no output. Weekly cadence is broken — meaning if trades
   *had* happened in W20, no honest-edge record exists. Add a check
   inside the task to error-out when its own output file is missing
   from the previous week.

5. **Walk-forward harness not re-run after Phase-A fixes.** ADR-013
   §A landed eight major Phase-A fixes (ADX router, log_trade SQL,
   sqzmom ATR stops, indicator alignment, etc.) and Phase-B harness
   extensions. `backtesting/results/` has been untouched since
   2025-12-06. The defining acceptance evidence for un-pause
   simply does not exist in updated form.

6. **Chronic API-reach blindness.** Three consecutive scheduled-task
   runs (premarket 2026-05-08, runtime-check 2026-05-09,
   edge-audit W19 + W21) have been unable to reach `localhost:8000`
   from the cloud sandbox. Every audit since has been filesystem
   inference only. If trades start firing today, this audit will
   still be blind tomorrow. **Wire a host-side runner before the
   first paper trade closes,** otherwise an entire armed-bot week
   could pass with zero authoritative trade data captured.

7. **`MAX_RISK_MULTIPLIER` is a dead variable.** Carry-over from
   W19. Operator-set value in `services/trading-engine/.env` is
   ignored; real sizing uses `ensemble_confidence_size_multiplier`
   (default 3.7). Same illusion-of-control as red flag #3.

8. **GRU models 4+ months stale and gated off.** Unchanged. Don't
   unfreeze without DSR > 0.95 on log-returns target.

9. **Pre-LIVE checklist gap on per-trade cap.** Pydantic field
   `max_risk_per_trade` accepts up to 0.5; no LIVE-mode validator
   refuses `> 0.02` when `TRADING_MODE=LIVE`. ADR-010 explicitly
   defers. Not relevant today (still PAPER), but the un-pause
   moment is a good time to land the validator so it can't be

## Recommendations

Grounded in red flags above. Numbered for tracking.

1. **Re-run the walk-forward harness against current Phase-A
   code before letting the un-pause stand.** Until a fresh
   `backtesting/results/*.json` shows OOS Sharpe > 1.0 (or any
   positive number, frankly) on at least one validated symbol,
   the un-pause is operating outside the very gate that justifies
   re-arming. Concrete: `python backtesting/run_walk_forward.py
   --symbol BTCUSDT --symbol ETHUSDT --symbol SOLUSDT
   --periods 5 --is-ratio 0.7` and publish the JSONs.

2. **Restore the 5% daily-loss cap.** Either edit
   `services/trading-engine/.env:108` from `MAX_DAILY_LOSS_PCT=10.0`
   → `5.0` to match CLAUDE.md, or file an ADR explaining the
   doubling. Status-quo (silent drift) is worst-of-both.

3. **Strip dead env vars or wire them up.** Either delete
   `MAX_DAILY_LOSS`, `ENABLE_AUTOMATIC_TRADING`, and
   `MAX_RISK_MULTIPLIER` from `.env` files, or add code that reads
   them. Live dead-vars give operators false confidence about what
   is in force.

4. **Wire a host-side audit runner.** Repeat of W19 rec #4 — three
   consecutive blind runs makes this load-bearing. Options:
   (a) Windows Task Scheduler invoking a WSL2 bash that hits
   `localhost:8000`, output piped into `reports/edge-audits/`;
   (b) Read-only public dashboard URL the cloud probe can hit;
   (c) Daily DB snapshot dumped into a repo-tracked file the
   sandbox audit can parse. Without one of these, an entire
   week of armed-bot trading can pass un-audited.

5. **File W20 stub or backfill.** Even a one-line "no run, no
   data" entry preserves cadence. Add a precondition to the task:
   if `reports/edge-audits/{ISO_LAST_WEEK}.md` is missing,
   write a minimal stub before the current-week report.

6. **Pre-LIVE per-trade-cap validator.** Land the
   `TRADING_MODE=LIVE → max_risk_per_trade ≤ 0.02` validator now.
   Pre-LIVE checklist item #1 per CLAUDE.md.

7. **When first trade closes**, run the audit immediately (don't
   wait for next scheduled cadence) with API reach restored.
   First-fill audit catches inverted R/R regressions, broken
   stop-loss limit-orders (Jan 2026 commit `380a674`), or silent
   look-ahead leakage faster than aggregated weekly stats can.
