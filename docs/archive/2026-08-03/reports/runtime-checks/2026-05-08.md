## Diagnosis
**STACK DOWN — from this audit's vantage point.**
- The audit env (sandbox) cannot reach the operator's Docker daemon or
  `localhost:8000`, so live state is unobservable here. That **does not
  mean** the user's stack is down — it means **this audit cannot
  distinguish** between "stack down on the user's host" and "stack up,
  but unreachable from sandbox". Operator should re-run the audit from
  inside the host shell to get real P&L.
- What static evidence does say:
  - Bot is configured to **run armed** (auto-trader on per compose default,
    paper mode, mainnet prices, ML/sentiment off).
  - **The file-based kill switch is currently broken** (EMERGENCY_STOP is
    a directory). If the auto-trader process is running, the operator's
    primary "halt now" lever does **not** halt it. Other kill paths
    (balance-based `KillSwitch.should_halt_trading`, daily-loss circuit)
    still apply.
  - The `MAX_DAILY_LOSS=0.10` line in `.env` is **dead config** — env var
    name doesn't match the pydantic field. The active daily-loss cap is
    the code default `5.0%`. Operator may believe they have a 10% cap
    when they actually have 5%.
- Without realized-P&L data, **no honest profitable / losing call** can
  be made. Anyone reading this section: do not infer "the bot is fine"
  from it being armed — armed and broken-kill-switch is worse than down.

## Recommendations
Ordered by impact. Anchored to evidence above.

### 1. Wrong now (today)
1. **Fix `EMERGENCY_STOP` mount.** `EMERGENCY_STOP` at repo root is a
   directory; `auto_trader.py:847-862` says this disables the file kill
   switch. On host:
   ```
   rmdir EMERGENCY_STOP        # only works because it's empty
   touch EMERGENCY_STOP        # explicit halt — auto-trader will refuse to run
   docker compose -f docker-compose.unified.yml up -d --force-recreate \
     trading-engine api-gateway
   ```
   Once the bind mount is healthy, decide deliberately whether to leave
   the file present (paused) or remove it (armed). Right now state is
   "looks paused, actually armed".
2. **Reconcile `PAPER_TRADING_INITIAL_BALANCE=10000.0` vs ADR-010 $100
   target.** Risk caps were recomputed for a `$100` balance ($10/trade
   at 10% cap). At $10,000 the same 10% cap is $1,000/trade — either
   intentional rebalance or stale env carrying old value. Check
   `paper_engine.get_balance()` log line at trading-engine boot.
3. **Re-run this audit from the host.** Sandbox can't reach Docker;
   re-run `health_check.sh` + the localhost endpoint set the task
   originally specified, and replace this report's "could not retrieve"
   sections with real numbers.

### 2. Missing
1. **Daily-loss env binding.** `MAX_DAILY_LOSS=0.10` in `.env` is
   silently ignored because the pydantic field is `max_daily_loss_pct`
   with no `alias="MAX_DAILY_LOSS"`. Either add a `validation_alias`
   so the env var binds, or rename it to `MAX_DAILY_LOSS_PCT` in `.env`
   and update the docs. Right now operator config is dead and the
   discrepancy is invisible.
2. **LIVE-mode caps validator.** `max_risk_per_trade` field accepts
   anything in `[0.001, 0.5]`; nothing forces `<= 0.02` when
   `trading_mode == 'LIVE'`. Add a model-level `model_validator`:
   `if trading_mode == 'LIVE' and max_risk_per_trade > 0.02: raise`.
   Today the only thing standing between 10% paper caps and 10% LIVE
   caps is operator memory. CLAUDE.md says "non-negotiable" but the
   code doesn't enforce it.
3. **Daily-loss + drawdown alert plumbing.** No evidence in static
   audit that the daily-loss circuit-breaker emits an external
   notification when it trips. `notification-service` exists; check
   it actually receives and forwards the trip event when the breaker
   triggers (`/verify-stack` would catch a silent trip).
4. **DSR/CPCV gate before re-enabling ML.** Per CLAUDE.md the GRU
   models lose to naive persistence after the look-ahead-leakage fix.
   Re-enabling `ENABLE_ML_PREDICTIONS=true` should be blocked by an
   automated DSR > 0.95 check on a holdout, not by env-var flip alone.

### 3. Improve
1. **Kill the dead `MAX_DAILY_LOSS=0.10` line** (or fix the binding,
   per Missing #1) — keeping a config line that does nothing is a
   trap for future-you.
2. **Reconcile CLAUDE.md vs `.env` re `AUTO_TRADING_ENABLED`.** Doc
   says it's set in `.env`, file says otherwise. Either restore the
   line so the doc is accurate, or delete the doc claim.
3. **Allocations vs documented winners** (`config.py:255-274`):
   `SOLUSDT: 0.30 / BTCUSDT: 0.25 / BNBUSDT: 0.20 / ADAUSDT: 0.15 /
   ETHUSDT: 0.10`. Comment block cites SOL +$55.90 / 60% WR and ETH
   25-33% WR / -0.04% as basis. The comment is from 2026-01-19 — six
   weeks of paper-trade since then. Pull realized P&L per symbol from
   `/api/trading/trades` once reachable; if SOL is still carrying and
   ETH still bleeds, this allocation holds. If it's flipped, this
   audit can't see it from static config — it's the most likely
   useful re-tune signal once the runtime is reachable.
