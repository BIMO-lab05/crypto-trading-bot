**Two viable disposition options (the planner has surfaced; executor MUST analyze both in DECISION.md):**

1. **Delete-all** — Remove the entire `scripts/monitoring/` directory. No tier-1 monitoring at the cron level. Pros: zero tier-2 attack surface; matches the spirit of "no unattended loops." Cons: loses the cheap tier-1 health checks (curl-and-log only); operator must check manually or reach for a separate Prometheus alertmanager flow.

2. **Keep-tier1-delete-tier2** (planner's strong recommendation per advisor input) — Retain `tier1_monitor.py` + `run_monitor.sh` + the operator helpers; DELETE `tier2_escalate.sh`, `tier2_mission.md`, `auto_pr_janitor.sh`. Tier-1 remains as cheap-and-honest cron health checks (curl + log). When tier-1 fails, the operator gets the alert and decides what to do. No claude invocation, no auto-PR, no agentic loop. Pros: preserves the operationally-valuable tier-1 monitoring; eliminates the high-blast-radius tier-2 surface; aligns with CLAUDE.md "checkpointed iteration only" rule. Cons: lose the autonomous-fix dream; operator latency on overnight failures.

**Excluded (during plan revision):** A `wire_with_bounds` option (gate `tier2_escalate.sh` behind an `ALLOW_TIER2=true` env var, document blast-radius bounds in README) was originally surfaced by the planner. It was dropped because adding only a runtime guard does NOT remove the `claude -p` invocation at `scripts/monitoring/tier2_escalate.sh:102`, so Task 2's grep gate (`! grep -rE 'claude\s+-p' scripts/monitoring/`) would deterministically fail under that option. Removing the literal invocation would collapse the option into either delete-all or a substantial rewrite outside this plan's scope. DECISION.md must include a one-paragraph note acknowledging this exclusion (per the plan-revision history) so future contributors see why only two options were considered.

The DECISION.md must analyze both with a STRIDE threat enumeration of the **current** tier-2 system as the baseline:
- **T-tier2-01 (Spoofing):** $FAILURE_JSON path forwarded to claude as env var; if any tier-1 check is fed by attacker-controllable data (CoinGecko response, Prometheus alert text, docker logs), prompt-injection becomes possible.
- **T-tier2-02 (Tampering):** claude has full filesystem write access to repo root; could modify any file before opening PR.
- **T-tier2-03 (Repudiation):** logs go to `logs/monitor_tier2.log` — no commit signing, no audit trail beyond text logs.
- **T-tier2-04 (Information disclosure):** `GH_TOKEN` available to claude via inherited env; mission prompt could be coaxed to print/exfiltrate.
- **T-tier2-05 (Denial of service):** mitigated (DAILY_BUDGET, MAX_OPEN_AUTO_PRS, single-flight flock).
- **T-tier2-06 (Elevation of Privilege):** auto-PR runs CI; CI workflows have additional secrets (CODECOV_TOKEN, etc.); a malicious PR could exfiltrate via CI logs.
