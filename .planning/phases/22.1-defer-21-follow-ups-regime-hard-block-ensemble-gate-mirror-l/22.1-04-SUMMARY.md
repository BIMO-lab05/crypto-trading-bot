# Phase 22.1 Plan 04: ADX Lookback Single-Sourcing + Capital Literal Cleanup Summary

One number declared three times is now declared once: `Settings.adx_period` replaces `TrendFollowingConfig.adx_period`, the `ADX_PERIOD` module constant and a dead constructor parameter, with signature pins and comment-safe source guards proving they cannot return; four text sites stop teaching bare account-equity literals.

## What Was Built

### Task 1 — `Settings.adx_period` (commit `2891d38`)

`app/config.py` gained a third tranche in the mirror-literal cluster:
`adx_period: int = Field(default=14, ge=2, le=200, ...)`, description naming
`default_adx_period` (its technical-analysis counterpart, TA `app/config.py:191`).
The cluster comment states plainly that these strategies compute ADX **locally**
and that this is therefore an engine-side declaration, not a request parameter.

`app/strategies/trend_following.py`:
- `TrendFollowingConfig.adx_period` dataclass field — deleted, replaced by a
  removal-rationale comment.
- `"adx_period"` key in `TrendFollowingConfig.to_dict()` — deleted.
- `_calculate_adx` now resolves `get_settings().adx_period` per call.

`app/strategies/trend_following_strategy.py`:
- `ADX_PERIOD = 14` module constant — deleted, replaced by a rationale comment.
- `adx_period` constructor parameter, its docstring line, the `self.adx_period`
  assignment and the startup log line printing it — all deleted. The docstring
  gained a `Note:` following the `aggregation/market_regime.py:125-147`
  precedent.
- `_calculate_adx(self, df, period: Optional[int] = None)` resolves the setting
  **in the body**. A Settings read in a parameter default freezes at import
  (`.claude/rules/money.md`).
- The warm-up length check reads `get_settings().adx_period`.
- The `"period"` key in the `get_strategy_params()` ADX reporting dict — deleted.

Verified: `get_settings().adx_period` prints `14`; constructor parameters are now
`['self', 'ema_fast', 'ema_medium', 'ema_slow', 'atr_period', 'enable_pyramiding']`;
`git diff --unified=0 app/strategies/ | grep -E '^\+(import |from )'` shows
exactly the two `get_settings` imports and nothing else.

### Task 2 — dead-arg pins and comment-safe guards (same commit)

`tests/test_engine_param_omission.py` went from **4 to 19 collected tests**
(+15). The module docstring gained a paragraph explaining why these sites need a

Added:

3. Settings-value pin — `get_settings().adx_period == 14`, message naming both

### Task 3 — capital literals (commit `4802248`)

- `app/risk/dynamic_risk_budget.py`: the usage example now calls

### 3. PATTERNS correction C-1, restated explicitly

**There was never an ADX request in these files to omit a parameter from.**

The upstream citations (`22.1-CONTEXT.md` decision C, `deferred-items.md`
DEFER-21-04) say `trend_following_strategy.py:1551` "is load-bearing: stops
sending `"period": self.adx_period` on the ADX request." That describes a
mechanism that does not exist. Re-verified on this branch:

- Neither `trend_following.py` nor `trend_following_strategy.py` contains any
  HTTP client. Both compute ADX **locally** from OHLCV arrays, in
  `_calculate_adx` methods defined inside each file.
- `:1551` was a key inside `get_strategy_params()` (enclosing `def` at `:1535`),
  a **params-reporting** method for logging and debugging output.

Consequently:
- The applicable precedent was the **constructor-parameter deletion** half of
  P21-7 (`aggregation/market_regime.py:125-147`), not its request-omission half.
- The applicable test shape was the `inspect.signature` dead-arg pin, **not** a
  captured-params `OMISSION_CONTRACT` row. Adding contract rows would have been
  vacuous by construction: that parametrization drives a fetcher and inspects
  the params it put on the wire, and these classes issue no request.
- The phrase "stops sending on the ADX request" appears **nowhere** in the code,
  comments, tests or this summary as a description of what changed.

This is recorded in the `config.py` cluster comment and in the extended
`test_engine_param_omission.py` module docstring, so the next reader hits the
correction at the source rather than having to find this file.

## Deviations from Plan

### Auto-fixed / deliberate adjustments

**1. [Rule 2 - Missing critical documentation] `config_overrides` silently drops `adx_period`**

- **Found during:** Task 1, while running the consumer grep.
- **Issue:** `create_trend_following_strategy` applies overrides via
  `if hasattr(config, key): setattr(config, key, value)`. Before this change
  `config_overrides={"adx_period": 20}` worked. After deleting the dataclass
  field, `hasattr` returns `False` and the override is **silently dropped** —
  reintroducing the exact "caller sets it, sees no error, gets no effect" shape
  this plan exists to remove, one layer out.
- **Resolution:** No in-repo caller passes it (the only factory call,
  `tests/test_multi_strategy_orchestration.py:159`, passes `symbols` and
  `timeframe` only), so this is not a blocker and no code change was made.
  Documented instead: the removal-rationale comment at the deleted dataclass
  field names this consequence explicitly, and the `config.py` cluster comment
  repeats it. A future caller reaching for that override key finds out why it
  does nothing.
- **Files modified:** `trend_following.py`, `config.py` (comments only).
- **Commit:** `2891d38`

**2. [Rule 2 - Consistency] `period or` → `period is None` in `trend_following.py`**

- **Found during:** Task 1.
- **Issue:** The plan said keep the existing caller-supplied-period-wins
  behaviour, whose current form is `period = period or ...`. `or` treats `0` as
  absent, and the sibling file was being changed to the `is None` form.
- **Fix:** Used `period = get_settings().adx_period if period is None else period`
  in **both** files. Behaviour is unchanged for every sane input (a period of 0
  is not a valid lookback); the point is that two files single-sourcing one
  number now resolve it with one idiom. Divergent idioms are how the next audit
  finds a fourth declaration.
- **Commit:** `2891d38`

**3. [Rule 1 - Incomplete gate] `startup.sh` carried two more bare account numbers**

- **Found during:** Task 3.
- **Issue:** The plan's acceptance greps are `grep -n 'THE ACCOUNT IS'` and
  `grep -nE '\$100\b'`. The original comment's lines 363-364 read *"ended up at
  10000 against a total_value of 100 (AUDIT 2.2)"* — no `$` prefix, so **both
  gates would have passed while a bare `10000` and a bare `100` survived** in
  the comment the plan told me to strip of account numbers. Passing the grep is
  not the same as satisfying the instruction.
- **Fix:** Rewrote the whole block (originally `:359-364`) with no account
  digits at all, keeping the AUDIT 2.2 reference and the refuse-to-guess
  rationale. `ADR-029` and `AUDIT 2.2` are document identifiers, not account
  sizes, and one of them is a required acceptance criterion.
- **Commit:** `4802248`

### Rejected fallback

The plan offered "keep the reporting key and report the resolved value" if the
consumer grep found an unanticipated consumer. The grep found none (see Evidence
§1), so both keys were deleted as the plan's default instructs.
