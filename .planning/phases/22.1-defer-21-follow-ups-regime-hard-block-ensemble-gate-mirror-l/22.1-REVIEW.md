## Warnings

### WR-01: Adopted regime confidence is not range-validated; bool coerces to 1.0

**File:** `services/trading-engine/app/handlers/signals.py:235-251` (consumer at `:318-320`)
**Issue:** The new adoption path validates that TA's `confidence` is coercible
and finite, but not that it is in [0, 1]. Two consequences:
1. Any finite out-of-range float — e.g. a percent-scale `62.0` from a TA-side
   regression — is adopted verbatim and multiplied into the risk-leg weight
   (`risk_confidence * 0.15`), silently inflating that leg ~124x relative to
   neutral and letting it dominate the weighted signal direction. TA clamps to
   [0, 1] today (`adx.py:328`), but this handler now trusts a cross-service
   payload it was just hardened against for NaN/inf — the range gap is the
   remaining hole in the same trust boundary, in a repo whose rules call units
   "a live trap".
2. A JSON `true` arrives as Python `bool`, and `float(True)` returns `1.0`
   cleanly, so a malformed boolean is adopted as maximum confidence instead of
   being omitted like the other malformed shapes in the test grid (which covers
   string/null/dict/list/nan/inf but not bool or out-of-range).

Impact is latent — the only arithmetic consumer is the enhanced path, currently
unreachable (DEFER-22.1-01) — but this phase's own rationale for the NaN/inf
check ("coercible is not the test that matters") applies identically here.
**Fix:**
```python
if (
    parsed_confidence is None
    or isinstance(raw_confidence, bool)
    or not math.isfinite(parsed_confidence)
    or not 0.0 <= parsed_confidence <= 1.0
):
    logger.warning(...)  # existing message
else:
    regime_report["confidence"] = parsed_confidence
```
(and add `true`/`7.0`/`-1.0` cases to the malformed grid in
`tests/aggregation/test_mirror_literals.py`).

### WR-02: Fetch-failure fallback still reports a present constant confidence 0.5

**File:** `services/trading-engine/app/handlers/signals.py:261`
**Issue:** DEFER-21-05's stated principle is "report the confidence TA
COMPUTED, not a constant standing where a measurement is expected", and the
success path now omits the key when TA supplies none. The `except` branch of
the SAME function still returns `"confidence": 0.5` — a present constant that
is indistinguishable from a real measurement in the API response (embedded at
`:138` as `"market_regime": market_regime`), which is the exact defect class
this fix was opened for. The adjacent `adx` key in the same fallback dict was
already converted to absence-stays-absent ("a plausible stand-in reads as a
real one in the API response" — that comment sits two lines above the offending
constant). Numerically inert at the arithmetic consumer (a present 0.5 equals
the defaulted 0.5 from `.get("confidence", 0.5)`), so this is a consistency and
API-honesty defect, not a behavior change.
**Fix:** Drop `"confidence": 0.5` from the fallback dict. The `reason` key
already marks the reply as a failure, and the consumer's declared neutral
produces the identical weight.

### IN-01: `rsi_period` bounds do not match the TA route bounds the comment claims

**File:** `services/trading-engine/app/config.py:394-397`
**Issue:** The tranche comment states "The ge/le bounds below are deliberately
the bounds technical-analysis already enforces on its own routes." True for
`bollinger_std_dev` (1.0-4.0 matches TA `handlers/indicators.py:83`) and
`trend_filter_kline_limit` (200-1000 matches TA `main.py:386`), but TA's RSI
routes allow `ge=2, le=200` (`handlers/indicators.py:25`, `main.py:283`) while
the engine field caps at `le=100`. Safe direction — every engine-legal value is
TA-legal, so no 422 can result — but an operator override of `RSI_PERIOD=150`
(TA-legal) fails engine Settings construction, and the comment's claimed
contract is wrong for one of its three fields.
**Fix:** Either widen to `le=200` or amend the comment to say the RSI bound is
deliberately tighter than TA's.

### IN-03: Harness empty-corpus guard is unreachable — `compare()` crashes first

**File:** `services/trading-engine/scripts/measure_regime_confidence_adoption.py:465-467` (crash site `:302`)
**Issue:** The integrity check `if result["row_count"] == 0: FAIL` runs after
`compare(corpus, per_arm)` at `:406`, but `compare` calls
`max(rows, key=...)` at `:302`, which raises `ValueError: max() arg is an empty
sequence` on an empty corpus — so the graceful FAIL path can never execute.
Unreachable today (the grid is non-empty by construction since `ENGINE_REGIMES`
always contains `UNKNOWN`), so this is dead code documenting a failure mode the
script would actually express as a traceback.
**Fix:** Check `if not corpus` before calling `compare()`, or guard
`biggest_mover` with `max(..., default=None)`.

### IN-04: New Settings fields bind to generic, unprefixed env names

**File:** `services/trading-engine/app/config.py:394,404,416,458`
**Issue:** Settings declares no `env_prefix` and sets `env_file=".env"`
(`config.py:1052-1053`), so the four new fields bind to `RSI_PERIOD`,
`BOLLINGER_STD_DEV`, `TREND_FILTER_KLINE_LIMIT`, and `ADX_PERIOD` — names
generic enough to exist in an operator `.env` or shell environment for another
purpose. `docker-compose.unified.yml` defines none of them today, and the
operator `.env` could not be inspected during this review (read denied), so
this is exposure, not a confirmed collision: any pre-existing variable with one
of these names would now silently retune the engine's traded signal path.
**Fix:** No code change required now; verify the operator `.env` does not
define these names before the next deploy, and consider a `TRADING_ENGINE_`
prefix if further generic names accrue.
