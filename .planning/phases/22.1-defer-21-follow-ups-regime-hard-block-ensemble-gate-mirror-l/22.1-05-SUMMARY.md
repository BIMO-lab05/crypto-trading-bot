## The absent-key decision and the arithmetic that forces it

`_calculate_enhanced_signal` (`handlers/signals.py:278-280`) is the only arithmetic consumer:

```python
risk_confidence = market_regime.get("confidence", 0.5)
weights.append(risk_confidence * 0.15)
```

`dict.get(key, default)` returns `None` for a **present** null — the default never fires — and `None * 0.15` raises `TypeError`. That exception is caught by the function's own broad `except Exception`, which returns the unmodified signal. So a present-`None` confidence would silently degrade the entire enhanced path on every TA reply lacking the key, with nothing visible at the boundary.

An **absent** key lands on the consumer's declared 0.5 neutral instead. Hence the deliberate divergence from the sibling `adx` handling three lines above, which reports a present `None` — `adx` is surfaced for display and never multiplied, so it can afford the other convention. The divergence is commented at the site and pinned by two tests.

**This is why "no exception escaped" is not an acceptable assertion here.** Because the function swallows everything, a poisoned risk leg and a healthy one are indistinguishable from outside. The discriminating test asserts the arithmetic *completed*: `metadata["enhanced"] is True`, `metadata["individual_signals"]["risk_adjustment"]["confidence"] == 0.5`, and zero ERROR records on `app.handlers.signals`.

| Reverse-order replay identical | `True` |

**Do not over-read "0 label changes."** It is a weaker statement than it looks, and the mechanism matters. `_get_risk_adjusted_signal` returns `HOLD` on every branch, so the risk leg's numeric value is always `0.0` — the regime confidence only ever moves `total_weight`, the *denominator*. Lowering it therefore **increases** `|final_signal_numeric|`, so a label can only move further away from HOLD, never between BUY and SELL. Zero changes means no row happened to sit inside the ±0.1 HOLD band where the shift would cross a boundary. It does **not** mean this value can never flip a label.

**Read the caveats before quoting any of that.** No P&L, no DSR, no CPCV, no edge claim (CLAUDE.md §2). This is signal composition only.

## Live impact: nil, and now proven rather than asserted

The plan expected ~zero live impact because live trading runs the **ensemble** path (`strategies/multi_strategy_ensemble.py` via `auto_trader`), not the enhanced path. That holds — and execution turned up a second, stronger reason.

The enhanced path is reachable only through `GET /api/v1/signals/enhanced/{symbol}` (`app/main.py:585-601`). That handler passes the aggregator's `TradingSignal` straight into `_calculate_enhanced_signal`, which reads `base_signal.signal.action` — and `TradingSignal` (`app/models/signal.py`) has **no `.signal` attribute**. Verified empirically on this tree 2026-08-28:

```
RAISED: AttributeError 'TradingSignal' object has no attribute 'signal'
```

The call raises on its first statement, the inner `except` re-raises on `return base_signal.signal`, and `get_enhanced_trading_signal`'s outer handler falls back to the basic signal. **The removed 0.7 therefore influenced nothing in production — not the arithmetic, and not `metadata.market_regime` either, since the `SignalResponse` construction is unreachable.**

Consequently every delta in the table above is a **counterfactual** — what the risk leg *would* do once the enhanced path is wired — not a change in observed behaviour. That framing is recorded in the script docstring and in the artifact's `is_not` field, so it travels with the numbers.

## Decisions Made

1. **Omit the key rather than return a present `None`** — locked by the planner, and independently confirmed by the arithmetic above. Pinned by a counter-case test.
2. **Warn only on a present-but-unusable value, never on absence.** Absence is TA's normal "no measurement"; warning on it would log on every call and bury the real signal. Asserted by `test_an_absent_confidence_is_not_logged_as_malformed`.
3. **Do not repair the enhanced-path wiring** (see Discovered / out of scope). Repairing it converts a dead money-adjacent endpoint into a live one — unscoped, and it would falsify the plan's own declared expectation mid-execution.
4. **Capture the discarded final label by wrapping `_numeric_to_signal`, not by re-deriving it.** The threshold logic stays in production code and is called unchanged; the harness only records what it returned.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 — missing critical validation] NaN/inf confidence would pass a bare `float()` guard and poison the weight arithmetic**

- **Found during:** Task 1 (writing the malformed-value coverage)
- **Issue:** The plan specified a guarded `float()` catching `TypeError`/`ValueError`. That is necessary but not sufficient: `float("nan")` and `float("inf")` succeed. A NaN confidence propagates through `risk_confidence * 0.15` into `total_weight`, makes `final_signal_numeric` NaN (which `_numeric_to_signal` silently resolves to HOLD), and lands NaN on the signal's `confidence` field. Threat register row T-22.1-05-01 requires that a malformed value is "never propagated into the weight arithmetic" — coercibility alone does not deliver that.
- **Fix:** Added `math.isfinite()` to the same rejection branch; NaN and inf are logged and omitted exactly like `"high"` or `{}`.
- **Files modified:** `services/trading-engine/app/handlers/signals.py` (`import math` + finiteness check)
- **Verification:** `nan` and `inf` added as ids to `test_a_malformed_confidence_is_omitted_not_propagated`; both pass, both fail without the guard.
- **Committed in:** `8be5ed8`

**2. [Rule 2 — deviation from a literal plan instruction, for correctness] Present-`None` vs absent distinguished via `"confidence" in payload`, not via a sentinel default**

- **Found during:** Task 1
- **Issue:** The plan's `key_links` contract requires the literal form `payload.get("confidence")`, which cannot distinguish an absent key from a present null — yet the plan's behaviour spec requires a *warning* for a present null and *silence* for absence.
- **Fix:** Membership test `if "confidence" in payload:` gates the block; the literal `payload.get("confidence")` is preserved inside it. Both the contract and the behaviour spec are satisfied.
- **Files modified:** `services/trading-engine/app/handlers/signals.py`
- **Verification:** `test_a_malformed_confidence_is_omitted_not_propagated[null]` (warns) and `test_an_absent_confidence_is_not_logged_as_malformed` (silent) are complementary and both pass.
- **Committed in:** `8be5ed8`

**3. [Rule 3 — plan assumption did not hold] The measurement cannot read the final label off the function's output**

- **Found during:** Task 2
- **Issue:** The plan asked the harness to report "the final signal label" per row. `_calculate_enhanced_signal` computes `final_signal` at `handlers/signals.py:332` and **never stores it** — only `confidence` is written back. The label is not observable from the returned object, and re-deriving it in the harness would have meant re-implementing production threshold logic, which the ablation-analog conventions forbid.
- **Fix:** The harness wraps the module's own `_numeric_to_signal` with a recording delegate. The reported label is the one production computed, on the real call.
- **Files modified:** `services/trading-engine/scripts/measure_regime_confidence_adoption.py`
- **Verification:** Determinism check passes; the recorded label is populated on all 432 rows in both arms.
- **Committed in:** `b5204ee`

## Discovered, out of scope — recommend deferring

Neither was caused by this change; both are pre-existing and both are recorded here rather than repaired, because repairing them is unscoped behaviour change on a money-adjacent path.

**Proposed DEFER-22.1-01 — the enhanced-signal endpoint never executes its own arithmetic.**
`get_enhanced_trading_signal` hands `_calculate_enhanced_signal` a bare `TradingSignal`; the function reads `base_signal.signal.*`, which does not exist on that type. Every request to `GET /api/v1/signals/enhanced/{symbol}` raises `AttributeError` internally and silently returns the plain signal. Evidence: the empirical probe quoted above, and the fact that the whole endpoint contract (ML weighting, regime multiplier, win-rate factor) is dead. **Repairing this is a real behaviour change** — it would activate an untested weighting path that has never run in production — and it needs its own plan, its own tests, and probably its own ablation.

**Proposed DEFER-22.1-02 — `final_signal` is computed and discarded (`handlers/signals.py:332`).**
Even once DEFER-22.1-01 is fixed, the "enhanced" signal cannot change a signal's *action*: the weighted label is computed and thrown away, and only `confidence` is written back. Worth resolving in the same plan as the above, since the intended behaviour of the endpoint has to be decided before either can be fixed.
