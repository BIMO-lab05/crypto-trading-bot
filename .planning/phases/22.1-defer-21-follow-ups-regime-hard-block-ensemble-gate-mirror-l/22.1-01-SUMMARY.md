# Phase 22.1 Plan 01: Aggregator Mirror Literals -> Settings Summary

Routed the last three `signal_aggregator.py` mirror literals (RSI lookback 9,
Bollinger band width 2.5, trend-filter kline count 300) through engine
`Settings` at unchanged values, with wiring tests proving each setting reaches
the outbound request.

## What Was Built

Each of these three numbers was a **second declaration** of a number the
technical-analysis service already declares. They agreed only by coincidence:
nothing read one from the other, so a single TA-side override would have moved
the TA number and left the engine sending the old one, silently, on the traded
path. Same defect class P21-7 closed at its own five sites.

### The three fields

| Field | Default | Bounds | TA counterpart | Call site |
|---|---|---|---|---|
| `rsi_period` | `9` | `ge=2, le=100` | `default_rsi_period` | `fetch_rsi` parameter default |
| `bollinger_std_dev` | `2.5` | `ge=1.0, le=4.0` | `default_bb_std` | `fetch_bollinger_bands` request params |
| `trend_filter_kline_limit` | `300` | `ge=200, le=1000` | `default_trend_limit` | `fetch_trend_filter` request params |

**NO VALUE CHANGED** — 9, 2.5 and 300 are the literals they replace.
`get_settings()` returns `9 2.5 300`, verified directly.

The BB and trend bounds are deliberately **technical-analysis's own route
bounds** (`Query(ge=1.0, le=4.0)` and `Query(ge=200, le=1000)`), so an
engine-side override that TA's endpoint would reject cannot even be declared —
it fails at Settings construction rather than arriving as a 422 from a service
that is not this one.

### Resolution shape

`fetch_rsi` took `period: Optional[int] = None` and resolves in the body:

```python
period = self.settings.rsi_period if period is None else period
```

A Settings read in the **parameter default** would freeze the value at import
(`.claude/rules/money.md`). An explicit caller-supplied period still outranks
the setting — pinned by a dedicated test, because
`tests/unit/test_signal_aggregator.py:125` calls `fetch_rsi(..., period=14)`.

The other two sites read `self.settings.<field>` directly inside the request
params dict, per call.

### Deliberate non-adoption of the omission contract

**This is the load-bearing note for future readers.** These three requests
**keep sending** their parameters. That is the *opposite* of the contract
`tests/test_engine_param_omission.py` holds for `fetch_sma` / `fetch_ema` /
`fetch_macd` / `fetch_ichimoku`, where the engine must **not** send what TA
owns. 22.1-CONTEXT item B locks engine-Settings routing here instead, and the
engine-side declaration is the mirror.

A one-line "do not convert this site to parameter omission" comment sits at
each of the three sites and in the config cluster comment, so the next reader
(or plan-checker) does not "fix" this into omission. None of the three fetchers
was added to `OMISSION_CONTRACT`.

### Wiring-test override values (the proof each setting reaches the wire)

| Test | Setting moved to | Asserted on the wire |
|---|---|---|
| `test_rsi_period_reaches_the_outbound_request` | `rsi_period = 11` | `params["period"] == 11` |
| `test_an_explicit_rsi_period_still_outranks_the_setting` | `rsi_period = 11`, caller passes `period=14` | `params["period"] == 14` |
| `test_bollinger_std_dev_reaches_the_outbound_request` | `bollinger_std_dev = 3.0` | `params["std_dev"] == 3.0` |
| `test_trend_filter_kline_limit_reaches_the_outbound_request` | `trend_filter_kline_limit = 500` | `params["limit"] == 500` |

A source grep proves a literal is gone; it does not prove the setting is wired.
These four move the setting off its default and assert the **captured outbound
params** carry the override.

**Vacuity guard.** All three fetchers wrap their bodies in
`except Exception: return None`, and `captured` is written *before* the payload
is parsed — so a stub missing one key would leave the params assertion passing
while the call silently failed. Every wiring test asserts the fetcher returned
non-`None` **first**. The trend payload also uses its own `result["data"]`
envelope rather than sharing the top-level shape the other two parse; reusing
one payload would have made `fetch_trend_filter` return `None` and the
assertion vacuous.

Per the plan, wiring was **not** verified by temporarily reverting a source
line and restoring it — every such write passes through the ruff format hook,
so a "restore" is not guaranteed byte-identical.

### Source guards

Three `BANNED_LITERALS` rows against `signal_aggregator.py`:
`r'period:\s*int\s*=\s*9\b'`, `r'"std_dev":\s*2\.5'`, `r'"limit":\s*300'`.

Proven effective by an in-memory check (no source mutation): each pattern
matches the pre-fix regression form and does **not** match the post-fix form.
The removal-rationale comments left at each site name the settings, never the
numbers, so they cannot trip their own guards.

## Deviations from Plan

### Corrections to plan text (no scope change)

**1. Method name: `fetch_bollinger` -> `fetch_bollinger_bands`**
- **Found during:** Task 1 (reading the source range)
- **Issue:** The plan and the objective refer to `fetch_bollinger`; the actual
  method in `signal_aggregator.py:220` is `fetch_bollinger_bands`. The plan's
  own acceptance-criteria grep (`"std_dev":\s*2\.5`) was unambiguous, so this
  was a naming slip in the plan text, not a wrong target.
- **Action:** Edited `fetch_bollinger_bands`. Recorded here so later plans in
  this phase do not re-inherit the wrong name.

**2. Docstring de-numbering at two sites (beyond the literal removal)**
- **Found during:** Task 1
- **Issue:** `fetch_rsi`'s docstring said "RSI(9) optimal for crypto markets"
  and `fetch_bollinger_bands`' said "Wider bands (2.5 SD)". Both restate the
  number the change just moved into Settings, so both would have gone stale
  silently on the first override — the exact failure mode the P21-7 doctrine
  calls out ("naming the setting rather than the number keeps this comment true
  the moment the setting moves").
- **Fix:** Reworded both to name the setting instead of the number. Confirmed
  first that no doc guard greps that wording (`RSI(9)` / `RESEARCH-BACKED`
  appear only in unrelated test prose). The separate 80/20 overbought/oversold
  paragraph in `fetch_rsi` was left untouched — it belongs to P21-8's doc guard.
- **Commit:** `59a0162`
