## The load-bearing finding: the images really were stale

Both target containers read "Up 7 hours" at baseline while the other twelve read "Up 2 days" — they had been recreated at ~17:17Z on 2026-08-27, *during* this phase but *before* its code landed. In that situation a passing content grep after the rebuild cannot, on its own, distinguish this plan's build from the earlier one.

So the check was run **before** rebuilding:

| Item | Identifier | Before rebuild | After rebuild |
|---|---|---|---|
| A | `REJECT_REGIME_BLOCKED` | absent (rc=1) | PRESENT |
| B | `rsi_period` in `config.py` | absent (rc=1) | PRESENT |

All four phase identifiers were absent from the images that had been serving. This is a content-level freshness proof that no timestamp argument can be waved away, and it is the direct mitigation for T-22.1-06-01 (Spoofing: "shipped" claimed from a stale container). **Had this plan not run, the six merged items would have been live on paper and absent from the running processes.**

### Why the counts are not compared directly

Two benign reasons, one exact and one flagged:

**Reconciled exactly.** The orchestrator's engine baseline of 2145 excluded the flake file; this run included it. `test_signal_cache.py` collects **33** tests, and `2178 − 33 = 2145` — the same measurement with and without one file. Separately, plans 01/02/04/05 added +16/+10/+15/+11 = **+52** engine tests and plan 03 added **+3** TA tests, so a raw count delta proves nothing regardless.

**Flagged, not smoothed over.** The orchestrator's handed-down TA baseline was **715**; this run measures **714**, `--collect-only` reports 714, and plan 22.1-03 independently measured 714 post-change (711 → 714, delta = exactly its 3 new tests). Three independent measurements agree on 714; the orchestrator's 715 is one higher than any of them and is most likely a transcription slip. It changes no verdict — both figures carry 0 failures — but it is recorded so a later phase does not silently inherit it.

## Near-miss worth recording: a cwd-relative pathspec produced a false empty diff

While checking what this phase changed under `services/technical-analysis/`, a `git diff --stat ca85d36..HEAD -- services/technical-analysis/` returned **empty**, which appeared to mean plan 03's SQZMOM work had never landed — alarming, since the rebuilt container demonstrably contained `is_unique`.

The command had been issued from *inside* `services/technical-analysis`, so the repo-relative pathspec resolved to a nonexistent nested path. Re-run from the repo root it reports **+37 / +260 lines across two files** and both plan-03 commits present. The work was always there.

The consequence for this plan is not the false alarm but its mirror image: **an empty `git diff` is exactly what this bug produces**, and the 21-05 narrowness pin is verified by an empty diff. That gate was therefore re-verified from the repo root with a positive control on a file that *did* change (`handlers/signals.py`, 60 lines) and with a direct blob comparison:

```
base ca85d36: 5af35770f5b3c2e1e39d930732feda7977784e90
HEAD ead5d6f: 5af35770f5b3c2e1e39d930732feda7977784e90
```

**Byte-identical.** The pin is untouched and green (11 passed). Every `git diff` reported in the evidence document was re-run from the repo root.

## Safety rails — observed in the running containers, not merely un-acted-upon

`safety/EMERGENCY_STOP` was **ABSENT at baseline and ABSENT after** — neither created nor removed. No container other than the two named was started, stopped or recreated, and no risk cap or `.env` line was edited.

That is a claim about operator conduct, and on its own it is not enough. **A `--force-recreate` re-reads `.env`, so the recreate is precisely the moment an edited or stale value would take effect.** The resulting state was therefore observed directly:

| Rail | Observed after recreate | Reading |
|---|---|---|
| `PAPER_TRADING_MODE` | `true` | Orders simulated — the decisive paper-mode flag is safe |
| `AUTO_TRADING_ENABLED` | `true` | **Armed** — the pre-existing `.env` operator override (CLAUDE.md §5), unchanged by this deploy |
| `PREFER_MAKER_ORDERS` | `false` | Unchanged default; the maker window stays an operator decision |
| `TRADING_MODE` | not set in container env | Not overridden toward LIVE |
| `LIVE_TRADING_ACK` | not set | Engine refuses to boot LIVE without it |

**Three of the four LIVE preconditions are provably unmet**, so this deploy did not move the system toward real money.

Note for the operator, stated plainly rather than buried: **the auto-trader remains ARMED and the kill-switch file is absent**, exactly as before this plan ran. Because trading-engine restarted, the loop now runs against item A's tightened admission path — a declared, operator-ratified behaviour change (fewer trades in counter-trend regimes), not a side effect of this deploy.

## Deviations from Plan

**None affecting scope.** The plan executed as written and no verification failed, so its stop-on-failure clause was never reached and no Rule 1/2/3 auto-fix was applied — correctly, since this plan is explicitly forbidden from repairing source.

Four additions beyond the plan's literal text, all strengthening gates rather than changing scope. The last three came out of review and are recorded as corrections to this plan's own verification, not to the deploy:

1. **Pre-build staleness probe (§1.6 of the evidence).** Not requested by the plan. Added because both target containers had been recreated mid-phase, which would have made a post-build-only content grep ambiguous.
2. **Positive control on the 21-05 pin diff (§3.6).** Not requested. Added after the cwd-relative pathspec near-miss above proved that an empty diff can be an artifact.
3. **[Rule 1 — bug in this plan's own verification] Item F's absence check could not detect a missing file.** The first prover used only a recursive `grep -rEq 'equity=10000' /app/app`, which returns rc 1 both when the literal is gone *and* when the file that held it was never in the image — the ERROR branch fires only if `/app/app` itself vanished. That is the same hole §2.1 claims to close, one level up, and it is why the plan's `<verify>` block names the two files individually. Added both per-file rows, kept the recursive sweep as a superset, and showed both files exist at non-trivial size (63,066 and 29,484 bytes) so neither gate is vacuous. Gate count rose 27 → 29.
4. **[Rule 2 — incomplete mitigation] T-22.1-06-04 was claimed from operator non-action alone.** The original evidence established that no mode flag was *edited*; it observed nothing about the containers that came up. **A `--force-recreate` re-reads `.env`, so the recreate is exactly when an edited or stale value takes effect.** Now verified in the running processes: `PAPER_TRADING_MODE=true`, `AUTO_TRADING_ENABLED=true` (the documented pre-existing override), `PREFER_MAKER_ORDERS=false`, with `TRADING_MODE` and `LIVE_TRADING_ACK` unset — three of the four LIVE preconditions provably unmet.

The plan's `<verify>` script was run **verbatim** (exit 0), after confirming `/app/app` is the correct in-container prefix for both services (`docker exec ... ls /app`) — the plan's own action text warns against assuming it. It was correct, so no rewrite was needed.
