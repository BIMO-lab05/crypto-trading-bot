All 14 containers were running and healthy at baseline. **No container was in an `exit=127` or restarting state, so the documented post-suspend bind-mount remedy was not needed and not applied** — nothing in this deploy should later be misread as an environment repair.

## The load-bearing finding: the images really were stale

Both target containers read "Up 7 hours" at baseline while the other twelve read "Up 2 days" — they had been recreated at ~17:17Z on 2026-08-27, *during* this phase but *before* its code landed. In that situation a passing content grep after the rebuild cannot, on its own, distinguish this plan's build from the earlier one.

So the check was run **before** rebuilding:

| Item | Identifier | Before rebuild | After rebuild |
|---|---|---|---|
| A | `REJECT_REGIME_BLOCKED` | absent (rc=1) | PRESENT |
| B | `rsi_period` in `config.py` | absent (rc=1) | PRESENT |
| D | `"confidence": 0.7` | **PRESENT at `:212`** | ABSENT |
| E | `is_unique` in `sqzmom_enhanced.py` | absent (rc=1) | PRESENT at `:892` |

All four phase identifiers were absent from the images that had been serving. This is a content-level freshness proof that no timestamp argument can be waved away, and it is the direct mitigation for T-22.1-06-01 (Spoofing: "shipped" claimed from a stale container). **Had this plan not run, the six merged items would have been live on paper and absent from the running processes.**

### Why the counts are not compared directly

Two benign reasons, one exact and one flagged:

**Reconciled exactly.** The orchestrator's engine baseline of 2145 excluded the flake file; this run included it. `test_signal_cache.py` collects **33** tests, and `2178 − 33 = 2145` — the same measurement with and without one file. Separately, plans 01/02/04/05 added +16/+10/+15/+11 = **+52** engine tests and plan 03 added **+3** TA tests, so a raw count delta proves nothing regardless.

**Flagged, not smoothed over.** The orchestrator's handed-down TA baseline was **715**; this run measures **714**, `--collect-only` reports 714, and plan 22.1-03 independently measured 714 post-change (711 → 714, delta = exactly its 3 new tests). Three independent measurements agree on 714; the orchestrator's 715 is one higher than any of them and is most likely a transcription slip. It changes no verdict — both figures carry 0 failures — but it is recorded so a later phase does not silently inherit it.

## Near-miss worth recording: a cwd-relative pathspec produced a false empty diff

While checking what this phase changed under `services/technical-analysis/`, a `git diff --stat ca85d36..HEAD -- services/technical-analysis/` returned **empty**, which appeared to mean plan 03's SQZMOM work had never landed — alarming, since the rebuilt container demonstrably contained `is_unique`.

The command had been issued from *inside* `services/technical-analysis`, so the repo-relative pathspec resolved to a nonexistent nested path. Re-run from the repo root it reports **+37 / +260 lines across two files** and both plan-03 commits present. The work was always there.

The consequence for this plan is not the false alarm but its mirror image: **an empty `git diff` is exactly what this bug produces**, and the 21-05 narrowness pin is verified by an empty diff. That gate was therefore re-verified from the repo root with a positive control on a file that *did* change (`handlers/signals.py`, 60 lines) and with a direct blob comparison:

```
base ca85d36: 5af35770f5b3c2e1e39d930732feda7977784e90
HEAD ead5d6f: 5af35770f5b3c2e1e39d930732feda7977784e90
```

**Byte-identical.** The pin is untouched and green (11 passed). Every `git diff` reported in the evidence document was re-run from the repo root.
