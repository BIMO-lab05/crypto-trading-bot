<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| backend response -> TileState rendering | TileState consumes axios error.response.data; potential reflection of server-controlled text in UI |
| operator click on Retry -> query.refetch() -> backend | Operator-triggered request, not unbounded |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-05-01 | Spoofing | server-controlled error.detail text shown in "Failed (...)" message | LOW | mitigate | TileState renders `error.response.data.detail` as a React text node `{detail}` (JSX-escaped). No HTML injection sink used. Same XSS baseline as the rest of the dashboard. Per D-14, raw `error.message` is forbidden (some libraries put untrusted bytes there); we use `error.response.statusText` as fallback. |
| T-06-05-02 | Information Disclosure | error message leaks backend stack trace | LOW | mitigate | D-14 explicitly forbids stack traces in TileState. The fallback chain is `detail -> statusText -> "request failed"` — never `error.message` (which may contain stack-trace fragments depending on axios config). |
| T-06-05-03 | Denial of Service | Retry button spam | LOW | accept | React Query's `refetch()` is idempotent and gated by its own dedupe; clicking Retry rapidly is harmless. No new rate limit needed at UI; gateway rate-limit middleware covers the per-IP case. |
| T-06-05-04 | Tampering | LABELED_STALE forceStale flag flipped to hide real failures | LOW | mitigate | `forceStale` controls only the stale-badge rendering, NOT the loading/empty/error path. A tile with verdict=LABELED_STALE that turns into a real error STILL shows "Failed (...)" — forceStale doesn't suppress error rendering. Verified by Task 1 behavior tests 3 + 7. |
| T-06-05-05 | Spoofing | REMOVED-verdict tile reintroduced via copy-paste | MEDIUM | mitigate | Plan 6-01's audit table is the inventory; Plan 7's Playwright smoke (DASH-06) will assert "each major tile renders non-empty" using the same inventory. Reintroducing a REMOVED tile without updating the audit table would fail the future smoke. For Phase 6, the operator review in Task 3 is the gate. |

No HIGH-severity threats. The most consequential risk (T-06-05-05 ghost tile reintroduction) is contained by the audit table being the authoritative inventory and Plan 7's smoke depending on it.
