Forced design decision (no choice to make):
- **Telegram path is direct `curl` to `api.telegram.org` from the runner.** The notification-service REST endpoint (port 8006) runs inside docker-compose on the operator's host; GitHub-hosted runners cannot reach it without VPN/tunnel. Direct curl is the only viable option AND the smaller blast radius (no service dependency, no networking). This is documented in the workflow header comment and threat model below.

Self-trigger prevention (advisor-flagged blocker):
- The workflow `name:` MUST NOT contain the literal `billing` (case-insensitive) or it would self-trigger: if the detector itself fails (Telegram 5xx, jq error, transient `gh api` flake), the next cron tick reads its own failure row's displayTitle, matches `billing`, and posts another alert — infinite loop. Therefore the workflow is named `CI Health Monitor (CIRESTORE-03)` (no `billing` literal) AND the jq filter has a `select(.name != "CI Health Monitor (CIRESTORE-03)")` clause as defense-in-depth (so even if the name is changed later to include `billing`, the self-trigger filter still catches it).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → Telegram Bot API | Direct outbound HTTPS to `api.telegram.org`. Token is GitHub repo secret; never crosses runner boundary as plaintext. |
| GitHub Actions runner → GitHub API | `gh run list` and `gh issue create` use `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}` (auto-injected, repo-scoped). |

| Detector self-data → detector logic | Detector reads `gh run list` which CAN include the detector's own prior failures. Self-trigger filter (`select(.name != "CI Health Monitor (CIRESTORE-03)")`) plus name-exclusion-of-`billing` literal prevent feedback loop. |
