<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator → harness | Operator supplies the run URL string. Must be regex-validated before any downstream use. |
| harness → gh CLI | Harness shells out to `gh api`. `gh` reads its own auth token; harness does not handle credentials. |
| harness → filesystem | Writes `ci-url.txt` and evidence JSON to operator-supplied paths (validated as absolute or relative to repo). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11.1-03-01 | Spoofing | URL arg | mitigate | Regex `^https://github\.com/...` rejects non-github URLs; numeric `run_id` enforced; subpath/query string allowed but not exec'd. No shell-eval of the URL. |
| T-11.1-03-02 | Tampering | --skip-gh-api in production | accept | `--skip-gh-api` is documented as offline/test-only; operator's commit of evidence records `skip_gh_api: true` so reviewers see when validation was skipped. The `_state` of LIVECLOSE-02 should never be flipped to `closed` based on `skip_gh_api: true` evidence; Plan 7 LIVECLOSE-INDEX.md should call this out. |
| T-11.1-03-03 | Information disclosure | gh token | accept | `gh` reads from its own keyring (`gh auth status`); harness does not log, print, or copy the token. |
| T-11.1-03-04 | Repudiation | wrong run linked | mitigate | Evidence JSON records `run_id`, `workflow_path`, `conclusion`, `workflow_name` — a future audit can re-query `gh api` against `run_id` to confirm. Operator commit history is the audit chain. |
| T-11.1-03-05 | Elevation of privilege | bash arg injection | mitigate | All args are quoted (`"$VAR"`); no `eval`, no `bash -c "$VAR"`. argparse subcommand on the Python side validates `--extra-json` is valid JSON before merge. |
</threat_model>
