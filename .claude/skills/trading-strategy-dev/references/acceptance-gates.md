# Acceptance gates

Canonical gates a change must clear before being declared "ready". A failed gate is not a vote — it's a stop.

## Rule-based strategy gate

For non-ML changes (new strategy, new param set, new filter):

| Metric | Threshold | Computed over |
|---|---|---|
| Sharpe (annualized) | > 0.8 | Blended SOL+BNB+ADA, daily returns |
| Max drawdown | < 25% | Same |
| Profit factor | > 1.2 | Same |
| Win rate | > 45% | Same |
| Risk-cap violations | 0 | Trade log audit |
| Walk-forward consistency | OOS Sharpe / IS Sharpe > 0.6 | Last 25% holdout |

If BTC/ETH are also tested (post 2026-05-03 re-add), they're informational — not part of the headline gate, since they were excluded historically and the strategy was not tuned for them.

## ML / signal-quality change gate

For changes to GRU models, signal scoring, or anything that returns a numeric forecast:

| Metric | Threshold | Notes |
|---|---|---|
| Deflated Sharpe Ratio | > 0.95 | See `leakage-tests.md` for formula |
| Outperforms naive persistence | yes | On log-returns, not direction |
| Look-ahead leakage tests | all pass | Per `leakage-tests.md` |
| Walk-forward folds | ≥ 5 | Each fold's Sharpe reported separately |

**Forbidden as headline metric**: directional accuracy. The V0 GRU rebuild incident (commit `c56765c`) showed how directional-accuracy gates can mask leakage.

## Engine-pipeline audit gate

For "verify the engine works" runs (no new code):

Every edge in `engine-pipeline.md` (A through L) must report PASS with a quoted evidence snippet. Aggregating to "engine OK" without per-edge evidence is a fail.

## Live-paper proof gate

Before declaring any code change shipped:

1. Service restarted after the change (CLAUDE.md: stale in-memory state).
2. One signal generated by the new code path observed in the `signals` table.
3. One order generated from that signal observed in the `orders` table (paper mode is fine — but the order row must exist).
4. One Telegram or email notification physically received.

HTTP 200 on `/health` is not on this list — it never has been.

## What to do when a gate fails

1. Report which gate, with the actual value next to the threshold.
2. Stop. Do not iterate live until the gate is honest.
3. Do NOT lower the threshold to fit the result. The thresholds are the contract.
4. If the user explicitly approves a lower threshold, document it in `wiki/decisions/` as a new ADR with rationale before re-running.
